## 3. 儀表板調整

- PASS / FAIL 圓餅縮成小格,放在良率左側,旁邊直接寫 PASS / FAIL 台數與比例。
- 空出的圖位改為**每小時產出**:07:00–19:00 每小時一根,PASS / FAIL 疊色;單一產品或工單時加一條每小時目標虛線(同 5A 的目標)。時間範圍取自設定頁的上下班時間(預設正是 07:00–19:00)。畫的是目前篩選範圍內最後有測試的那一天;上班時間外的台數寫在圖的右上角。

## 4. 5B 做了什麼

**工單詳情頁**(`#wo?wo=…`,從工單頁、失敗清單的工單號碼進入)
- 標頭:工單、產品、狀態燈、AI 一句話、測試期間、有測試的小時數。
- 8 格數字:已測 / 計畫、良率、FAIL(含主要原因)、重測率、2.4G / 5G 中位數(含同產品平常值)、每小時產出 vs 目標、最多連續 FAIL。
- 檢查結果、與上一張同產品工單的比較表(差異用 ▲▼ 與顏色標好壞;明顯變差另外標記)、良率趨勢、吞吐量分布、失敗機台清單(可下載 log)、網頁上傳批次(登入才看得到)。

**比較**(Q12:自動 + 手動):預設與同產品上一張比;下拉或工單頁勾兩張可比任意兩張。「明顯變差」= 良率少 1 個百分點、重測率多 2 個百分點、吞吐量或每小時產出少 20% 以上。

**管理者設定計畫數**(Q4):詳情頁直接設定,記在異動紀錄。撤銷上傳批次時**不會蓋掉管理者的值**:只重算「這一批設定的」計畫數,並在管理者的值與其他批次之間取較晚設定的(7 種先後順序都測過)。

**結構化結案報告(L3)**
- 事實表由伺服器產生、原樣顯示(可展開);AI 只寫**摘要、異常、可能原因、建議動作**,中英一次產生(Q24)。
- **每句話的數字都要對得上事實**(Q26),對不上的句子直接丟掉;摘要被丟掉就改用規則摘要。可能原因一律寫成「可能…」,並註明「請工程師確認」。
- 一般工單(沒有黃紅燈、也沒有明顯變差)只寫摘要,不會為了填滿段落而寫空話。
- 工單完成時自動產生(Q23),新的先;任何工單都可以按「產生報告 / 重新產生」(期中報告)。77 張已完成工單已在背景產生完成,平均每張 15 秒,沒有任何句子因數字不符被丟掉。
- 舊的五段式報告不再由畫面開啟,它的背景預熱已關閉(舊看板 `/legacy/` 仍可用)。

**追問**:只根據這張工單的事實回答,數字同樣核對;事實回答不了的會直說(例如問測試室溫度)。2–3 秒一題。

範例(紅燈工單 5101-260102014):

> 工單 5101-260102014 測試 594 台 TN-86_PICO-IMX7,良率 98.82%,高於 98% 的合格標準。
> **異常**:曾連續 4 台 FAIL;2.4G 吞吐量中位數 13.8 Mbps,比同產品平常低 26%
> **可能原因**:可能因測試站或夾具問題導致連續 FAIL;可能因 AP 或頻道設定異常導致 2.4G 吞吐量偏低
> **建議動作**:比對同產品其他工單的 2.4G 吞吐量與測試站設定(AP、頻道);確認連續 FAIL 的時段是否來自同一測試站或夾具

## 6. 試做中發現並修正的問題

| # | 問題 | 修正 |
|---|---|---|
| 1 | 撤銷上傳批次會用批次的計畫數蓋掉(或刪掉)管理者設定的值 | 只重算由該批次設定的計畫數,管理者的值另外保存 |
| 2 | 改了計畫數後,另一個 API 行程最多一分鐘內仍顯示舊值 | 狀態快取加上計畫數的變更時間 |
| 3 | 「每小時產出少 3.7」被數字核對擋掉(事實是 −3.7) | 核對允許變化量的絕對值 |
| 4 | 完全正常的工單被寫出「重測率上升 0.2」之類的異常與臆測原因 | 伺服器先判定「明顯變差」;一般工單只留摘要 |
| 5 | 報告用 UPH、重試率等詞,與看板用語不同;回答中出現 fail_streak 之類的欄位名稱 | 提示詞加用語表,禁止出現欄位名稱 |
