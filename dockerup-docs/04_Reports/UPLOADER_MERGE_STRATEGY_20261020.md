## 1. 桌面版上傳機制(網頁版要對齊的行為)

來源:`new_wifi_stress_log_analyzer.py` 的 `on_upload_to_db`(L1323 起)與 `log_parser.py`。兩版上傳邏輯相同(`new_` 檔頭註明「parsing / CSV-output / DB-upload logic is identical to the original」)。

| 桌面版步驟 | 實際行為 | 網頁版對應 |
|---|---|---|
| 選 Log Folder | 資料夾內的單筆 `.txt`,檔名 `YYYYMMDD_HHMMSS_SN_MAC1_MAC2_RESULT.txt` | 選 zip / 多檔 / 資料夾;**WiFi 的 log 已是單筆,不需要像 Solo_PIXI 那樣先切檔** |
| 填 **Product Name**、**Work Order**(必填,空白不給傳) | 上傳時 `record["product_model"]`、`record["work_order"]` **以使用者輸入覆蓋**,不是從路徑推斷 | 同樣覆蓋。**不可沿用 `/api/ingest`**:它用 `extract_path_meta` 從伺服器路徑推斷,行為不同 |
| 填 Server IP → `postgresql://qc:***@{host}/wifitest`,每 30 秒心跳 | 使用者電腦直連 DB 5432 | 改走 HTTPS/HTTP API,**使用者不再需要 DB 連線**(退役桌面版後可關 5432) |
| `scan_directory` 取 `*.txt` | 全部都處理 | 同 |
| `log_parser.ingest_file` | 讀檔(utf-8, errors=replace)、去 NUL、解析 KPI、算 SHA-256 | **直接重用同一支 `log_parser`**,不另寫解析 |
| `write_record` | `INSERT … ON CONFLICT (file_hash) DO NOTHING`,每筆 commit;回傳 None = 重複 → 略過 | 同(重複 = skip);改為每 50 筆 commit 以提速 |
| 進度/取消/結果 | 已處理/插入/重複/錯誤、NUL 清理檔數與位元組、Cancel Upload | NDJSON 串流進度;取消 = 中斷串流 + 伺服器旗標 |
| Resume from last upload log | 讀上次上傳紀錄,跳過已處理檔 | **不需要**:重傳時 hash 去重自動略過;改以「上傳紀錄」取代 |
| 寫上傳 log 檔 | 本機檔案 | `upload_log` 資料表(含上傳者、IP、對話、結果) |

**桌面版的三個缺口(網頁版要補)**:① 沒有紀錄是誰傳的;② 打錯工單/產品後因 hash 去重,**重傳無法修正**;③ 每台電腦都得裝 exe 並直連 DB。

### 1.1 實際交付格式(以你提供的範例 `5101-251216015.zip` 實測)

```
5101-251216015.zip                         ← 外層:以工單號命名(範例檔名前面多了系統加的 uuid 前綴,推斷工單時不能假設整個檔名就是工單號)
└─ 5101-251216015/                         ← 頂層資料夾 = 工單號
   ├─ TN-99_EDM1-IMX6P.zip                 ← ★ 內層 zip = 實際 log(252 個平鋪的 .txt,18.2MB,壓縮比約 7)
   ├─ TN-99_EDM1-IMX6P_all_sn_in_order.csv / _sn_pass_latest.csv / _sn_fail_latest.csv /
   │  _sn_overall_latest.csv / _sn_terminated_latest.csv / _sn_sequence_check.txt
   ├─ wifi_stress_report_TN-99_EDM1-IMX6P_20260203_112648.csv
   ├─ wifi_stress_sn_summary_…csv
   └─ wifi_stress_yield_TN-99_EDM1-IMX6P_20260203_112648.txt     ← 內含 "Product: TN-99_EDM1-IMX6P"
```

這是**桌面分析工具的產出再整包壓縮**。對網頁版 analyze 的影響:

| 發現 | 設計 |
|---|---|
| log 在**內層 zip** 裡,外層還有 7 個 CSV 與 2 個 `.txt` 報表 | analyze 必須支援**巢狀 zip(最多 2 層)**,也支援「直接一包 log 的 zip」與「選資料夾」三種輸入 |
| 外層的 2 個 `.txt`(`sn_sequence_check`、`yield`)**不是 log** | 以檔名格式過濾(不符 V2 格式者歸為「非 log 檔」,**列為 ℹ 忽略清單,不算錯誤**)。桌面版是選到 log 資料夾才掃,不會碰到;網頁版吃整包就會碰到 |
| 工單號在**外層檔名與頂層資料夾**;產品在**內層 zip 檔名、報表檔名、yield 報表內文** | 伺服器可推斷出「工單 `5101-251216015`、產品 `TN-99_EDM1-IMX6P`」。**用途是預填候選與交叉檢查**:AI 仍要求使用者自己提供/確認這兩項,使用者輸入與推斷不同 → ⚠ 提示(見 §4 R8)。推斷時用 `\d{4}-\d{9}` 在名稱中**搜尋**,不要求整個名稱相等 |
| 解壓後 18.2MB,壓縮後 2.6MB | 安全上限(見 §9):巢狀深度 ≤ 2、總解壓量 ≤ 1GB、單檔壓縮比 ≤ 50、檔案數 ≤ 20,000;拒絕絕對路徑、`..`、符號連結 |
| 檔名全部符合 V2 格式(`YYYYMMDD_HHMMSS_SN_MAC1_MAC2_RESULT.txt`);全 PASS;測試時間 2026-02-02 09:51:48 ~ 2026-02-03 08:27:10 | 與桌面版的 `parse_filename` 結果一致 |

**這批範例在 DB 的狀態**:252 個 SHA-256 **全部已存在**,且全屬於 `5101-251216015` / `TN-99_EDM1-IMX6P`(2026-04-30 入庫)。同一產品另有 7 個工單、共 2,990 筆,工單日期都符合 §3.3 的格式。所以它同時是**最佳的回放測試素材**(見 §8)。

## 2. 目標流程

```
① 提供 log        選 zip/資料夾 ──► POST /api/log-upload/analyze
                                    暫存、安全解壓(巢狀 zip ≤ 2 層、上限檢查)、
                                    掃 *.txt、驗檔名(非 log 檔列入忽略清單)、算 SHA-256、
                                    由包裝推斷工單/產品(僅供預填與交叉檢查)
                                    查 DB:哪些 hash 已存在、屬於哪個工單/產品
                  ◄── facts(有效檔數、無效檔名明細、時間範圍、已存在筆數)
② 提供產品名稱、   AI 對話(預設)或表單(AI 離線/使用者切換)
   工單號
③ 驗證            伺服器規則(第 4 節)──有 ⚠ 要勾「我確認無誤」
④ 確認上傳        POST /api/log-upload/commit(NDJSON 串流)
                  全域鎖 → upload_log=running → 逐筆 parse/INSERT(帶 upload_id)
⑤ 結果/紀錄/撤銷   done → 顯示結果;紀錄頁可依批次撤銷
```

**原則:規則有最終決定權,LLM 只負責對話、擷取與口語說明**(AI 的回覆不會直接觸發上傳,最後一定由使用者按「確認上傳」)。

**上傳前提(已確認)**:不論用哪種方式提供 log,都必須先填**工單號(沒有就輸入 `NOWO`)**、**完整格式的產品類別**與**計畫測試數量**,三項都通過 §3.3 / §3.6 的檢查,才能按「確認上傳」;格式一律依照既有資料庫。這個限制同時在前端(按鈕停用、即時提示)與伺服器(commit 重新驗證,失敗回 422)執行。

### 2.1 三種輸入方式的統一處理

| 輸入 | 瀏覽器端 | 伺服器端 |
|---|---|---|
| **巢狀 zip(標準交付,如範例)** | 單一檔案上傳 | 暫存 → 安全解壓外層 → 遇到內層 zip 再解壓(最多 2 層)→ 掃 `*.txt` |
| **直接一包 log 的 zip** | 單一檔案上傳 | 同上(只有一層) |
| **選資料夾** | `<input type="file" webkitdirectory>` 讀取**資料夾裡的所有檔案(含子資料夾)**;**以每批 ≤ 500 個檔案、≤ 50MB 分批**依序傳到同一個 `upload_id` 的暫存區,顯示進度,斷線可只重傳未完成的批次 | 全部批次到齊後視為一個「虛擬資料夾」,與上面兩種走**同一套掃描**:`*.txt` 取檔名有效者為 log;資料夾內若有 zip 同樣展開(≤ 2 層);其他檔案(CSV、報表等)進 ℹ 忽略清單 |

- **為什麼資料夾要分批**:Starlette 0.41.3(FastAPI 0.115.5 所用版本,已讀原始碼確認)預設**單一 multipart 請求最多 1000 個檔案**(`max_files=1000`),超過直接回 "Too many files";而最大工單有 **7,023 個檔**。分批同時帶來進度條與斷線續傳。
- 三種輸入最後都收斂成同一份「檔案清單 → 有效 log」,所以驗證與寫入邏輯完全相同(回放測試 F、G 驗證三者等價)。
- 瀏覽器傳來的相對路徑**一律視為不可信**:只用來顯示與推斷,**絕不用來組成檔案系統路徑**;暫存檔以伺服器產生的內部 id 命名,忽略含 `..`、絕對路徑、符號連結的項目。

## 3. AI 上傳協助設計

### 3.1 對話目標:收齊四項資料

伺服器維護「缺哪些」的狀態,**由伺服器決定下一個要問什麼**,LLM 只負責把使用者自由輸入擷取成欄位、並把規則結果講成人話:

| 缺項 | AI 的動作 | 驗證 |
|---|---|---|
| ① log | 對話區上方固定顯示拖放/選檔區;未選檔時 AI 回「請先選擇要上傳的 log(zip 或資料夾)」。選檔後由**伺服器直接產生開場白(不經 LLM,數字不會錯)**:「已讀取 N 個有效 log(M 個檔名無效),測試時間 A ~ B。請問這批是哪個產品?」 | 至少 1 個有效檔名 |
| ② 產品類別 | AI 明講格式與範例(`TN-86_PICO-IMX7`),並以**由資料庫提供、可點選的產品清單**(`GET /api/products/registry`,§3.4)讓使用者選擇——**這是預設做法**,清單目前 11 個,新產品寫入後下一位使用者立即看得到;使用者可用任何接受的寫法(`TN73_PICO_IMX6`、`tn-73_pico-imx6`)、只給 TN 編號(如「86」)或口語,由**伺服器**經辨認庫比對成**正式名稱**,AI 再請使用者確認 | 形狀錯誤 ❌;TN 編號已被其他產品使用 ❌(R16);形狀正確、編號未用過、但不在辨認庫 ⚠(新產品;上傳者與管理者皆可新增,見 R4) |
| ④ 計畫測試數量 | AI 問「這批的計畫測試數量是多少?」;純數字用規則抽取,中文數字/縮寫(「一千二」「1.2k」)才請 LLM 轉換,**轉換結果一律請使用者確認**;之後顯示數量對齊(§3.6) | 1–99,999 的正整數 ❌;> 10,000 ⚠;對齊結果 ℹ |
| ③ 工單號 | AI 明講格式與範例(`5101-260108007`),**並固定附上「沒有工單號請輸入 `NOWO`」**;**regex 為主**擷取,LLM 輔助;兩者不一致以 regex 為準 | 格式與日期 ❌;`NOWO` 不擋(ℹ);詳見 §3.3、§4 |

- **計畫測試數量是網頁版新增的要求**:桌面版沒有這個欄位,現有 schema 與程式也沒有計畫數/目標數的資料表,所以新增 `wo_plan` 儲存(§3.6)。
- **模式切換**:LLM 在線 → 預設對話;離線 → 直接表單。兩種模式隨時可切換、共用同一組已擷取的值。
- **降級**:單次 LLM 呼叫逾時 60 秒、或擷取連續失敗 2 次 → 自動切表單並保留已擷取的值。
- **Prompt 安全**:使用者輸入只當資料;system prompt 固定放最前(利於 prompt cache);只帶最近 10 輪;LLM 輸出不當指令執行。
- **API**:`POST /api/log-upload/chat`,NDJSON 串流 `extract → validation → delta* → done`(失敗送 `fallback`);單則訊息上限 500 字、最多 40 則;上傳者只能對自己 analyze 的 `upload_id` 對話。

### 3.3 固定格式規格(從現有 DB 歸納,不是憑空訂的)

| 欄位 | 格式 | 範例 | 資料依據 |
|---|---|---|---|
| **工單號** | `<前綴>-<YYMMDD><3 碼流水號>`,**前綴固定為 4 位數字(已確認,任何 4 位數字皆合法)或 `NOWO`(無工單號,見下)**。regex:`^(\d{4}\|NOWO)-\d{2}(0[1-9]\|1[0-2])(0[1-9]\|[12]\d\|3[01])\d{3}$`;**另須通過日曆檢查**(regex 擋不掉 2 月 30 日),流水號不可為 `000` | `5101-260108007`、`NOWO-260420001` | DB 77 個工單**全部符合**:76 個為 4 碼前綴(`5101` 75 個、`5105` 1 個),1 個為 `NOWO-260420001`;77 個的 YYMMDD **全是有效日期**(2024-12-25 ~ 2026-09-14),流水號 001–019 |
| **產品類別**(`product_model`) | **儲存與顯示用的正式名稱**:`TN-<編號>_<型號>`。**接受的輸入寫法**(正規化後經辨認庫比對成正式名稱,見 §3.4):`TN` 後的 `-` 可省略;編號與型號之間、型號內部的分隔可用 `-`、`_` 或空格。輸入形狀 regex:`^TN[-_ ]?\d{2,4}[-_ ]+[A-Z0-9][A-Z0-9 _-]*[A-Z0-9]$` | 正式名稱 `TN-86_PICO-IMX7`;可接受寫法 `TN73_PICO_IMX6` → 正式名稱 `TN-73_PICO-IMX6` | 現有 11 個正式名稱**全部符合**;TN 編號 11 個**互不重複**(73、86、99、111、112、165、167、175、228、250、410),編號可唯一對應產品。`TN-175_PICO-IMX8M MINI` **內含空格**,而桌面版 `_safe_name` 會把空格轉成底線(實測),所以它產生的檔名會變成 `…IMX8M_MINI`——**必須能對回正式名稱** |

- ⚠ 桌面版 Product Name 的 placeholder 是 `TNXXX-XXXX-XXXXXX`,**與實際資料的慣例不符**(過時提示)。網頁版的提示與範例一律用上表格式。
- **前綴規則(已確認)**:固定 4 位數字,任何 4 位數字都合法,**不設已知前綴白名單、不給警告**。(資料中目前只出現 `5101` 與 `5105`,兩者都出現在各產品上,與產品無對應關係。)
- 工單日期與首筆測試日期的差距實測為 **−6 ~ +469 天(中位數 37)**,已有工單日期晚於首筆測試 6 天的先例,所以**不拿工單日期去跟 log 時間做硬性比對**,只顯示。
- **無工單號(NOWO)——已確認「一律可上傳;沒有工單號就輸入 `NOWO`」**:
  - AI 問工單號時**一定要說明**「若這批沒有工單號,請輸入 `NOWO`」。使用者什麼都沒給、或回答「不知道」時,AI **不會自行當成無工單**,而是再問一次;只有使用者明確輸入 `NOWO`(不分大小寫、全形也可)才視為無工單。使用者若用口語說「沒有工單」,AI 會**請他確認**後才採用,不靜默接受。
  - **儲存值(我的預設)為 `NOWO-<今日 YYMMDD><流水號>`**,例如 2026-10-20 第一批 → `NOWO-261020001`,同日第二批 → `002`。流水號在上傳全域鎖內向 DB 取下一個未使用的值,並**顯示給使用者確認**;使用者也可以直接輸入完整的 `NOWO-YYMMDDnnn`(同樣檢查日期與流水號)。
  - **為什麼不直接存字面的 `NOWO`**:程式對 `NOWO` **沒有任何特殊處理**——dashboard 只排除空值/NULL 的工單,所以 `NOWO-…` 會被當成一般工單,出現在工單清單、`v_yield_by_wo`、Advanced 頁的產出與時間指標、AI Report。若所有無工單批次都存成同一個 `NOWO`,它們會被合併成一張「工單」,良率與產出速率混在一起而失去意義。既有的 `NOWO-260420001`(250 筆,TN-86,2026-04-17)就是這個慣例,所以沿用。
  - 無工單批次**仍需產品類別**(必填),並顯示 ℹ:「此批無工單號,Advanced 頁的工單產出指標僅供參考」。
  - 若你要的其實是**字面存成 `NOWO`**(所有無工單批次共用),是個小改動,但上述統計會混在一起(見 §10)。

**輸入正規化(伺服器端,先於驗證):** NFKC(全形數字/符號轉半形)、去前後空白、各種破折號(`–` `—` `－` `−`)統一為 `-`;工單號去除內部空白;產品名稱與 `NOWO` 的英文字母轉大寫、連續空白壓成一個。正規化後的值才送驗證,並**把正規化結果顯示給使用者確認**(例如「已將 `５１０１－２６０１０８００７` 轉為 `5101-260108007`」)。

**AI 如何「要求」並確保格式:**
1. **提問由伺服器產生**:每次要問產品或工單,問句與格式範例都來自伺服器模板,不靠 LLM 自己記得格式(工單的問句固定附帶「沒有工單號請輸入 `NOWO`」)。
2. **LLM 只能抄,不能補**:擷取結果必須是使用者原文(經正規化)的子字串,**伺服器逐字核對**;LLM 不得猜測、補齊或修正數字(例如使用者只打了 8 位數,不能自己補一位)。核對不過 = 視為沒有擷取到。
3. **錯誤由規則產生原因碼,LLM 只負責口語化**,例如 `wo_bad_shape`、`wo_bad_date`(「`261340` 不是有效日期,格式是 年月日 YYMMDD」)、`wo_seq_zero`、`product_bad_format`,並附範例。
4. **產品一律經辨認庫(§3.4)**:接受的寫法比對成正式名稱;只給 TN 編號或口語時,依編號/唯一子字串比對——唯一命中 → 請使用者確認;多個命中 → 以按鈕列出;形狀正確但沒有命中 → 新產品提案,需明確確認(⚠);形狀不正確 → 請使用者提供完整格式。
5. **同一欄位連續 3 次格式錯誤 → 該欄位改為表單輸入**(即時格式提示 + 產品下拉選單 + 範例),避免在對話裡來回糾纏。
6. **四項收齊後顯示摘要卡**(產品、工單、計畫測試數量與數量對齊、有效 log 數、已存在筆數與警告),由使用者按「確認上傳」;commit 時伺服器**重新正規化並重新驗證**,不信任前端或 LLM 的任何結果。
7. **表單模式用同一套規則**:`pattern` 屬性 + 即時錯誤訊息 + 產品下拉(含「其他(新產品)」選項)。

### 3.4 產品辨認庫(product registry)

需求:**建立產品名稱的資料庫,用來比對,在 AI 寫出的時候就擋得住。**

- **資料表 `product_registry`**(只新增,不改既有資料):`canonical`(正式名稱,PK,如 `TN-73_PICO-IMX6`)、`match_key`(UNIQUE;= 正式名稱轉大寫後去掉 `-`、`_`、空格,如 `TN73PICOIMX6`)、`tn_number`、`aliases`(額外別名,選填)、`source`(`seed` / `upload` / `admin`)、`created_by`、`created_at`、`status`(`active` / `retired`)。
- **初始資料**:migration 時由 `SELECT DISTINCT product_model FROM test_record` 帶入,目前 **11 筆**。已用原型驗證:11 個比對鍵互不衝突、TN 編號互不重複(1:1)。
- **比對流程(伺服器)**:輸入 → NFKC / 大寫 / 去空白 → 形狀檢查(§3.3)→ 轉比對鍵 → 查辨認庫:
  - **命中 → 一律改用庫內正式名稱**:`TN73_PICO_IMX6`、`tn-73_pico-imx6`、`TN-73 PICO-IMX6`、全形寫法,都 → `TN-73_PICO-IMX6`;`TN-175_PICO-IMX8M_MINI`(桌面版產出的檔名寫法)→ `TN-175_PICO-IMX8M MINI`。
  - **未命中,且該 TN 編號已被辨認庫中另一個產品使用 → 直接擋下(R16,已確認)**:畫面直接列出該既有產品與編輯距離 ≤ 2 的近似產品,讓使用者一鍵改選。
  - **未命中,且 TN 編號從未出現過 → 新產品提案**:`TN-<編號>_<型號>`,型號內的 `_` / 空格統一轉成 `-`(`TN88_NEW_BOARD` → `TN-88_NEW-BOARD`),**顯示提案請使用者確認**(R4)。
  - 已實測的防呆:打成 `TN-86_PICO-IMX6`(把 IMX7 打錯)→ **擋下**並建議 `TN-86_PICO-IMX7`;只打 `TN-99_EDM1`(被截斷)→ 編輯距離抓不到,但同編號檢查**擋下**並指向 `TN-99_EDM1-IMX6P`。**原型 18/18 案例符合預期(已用新規則重跑)**。
- **產品清單由資料庫提供(已確認的做法)**:`GET /api/products/registry`(需登入)回傳辨認庫中 `status=active` 的正式名稱,依最近使用排序、附筆數;對話模式以可點選按鈕呈現、表單模式以下拉選單呈現。**使用者平常只需「選」,不需要打字**;打字只用在新增產品。因為清單直接來自資料庫,新產品寫入後下一位使用者立即看得到,不需改程式。
- **新產品何時寫入**:使用者確認、且該批 commit 開始時,在同一個交易內寫入(`source` 與 `created_by` 記錄上傳者角色與帳號)。若該批最後一筆都沒寫入,或之後被撤銷而該產品已無任何資料,**一併移除**這筆辨認庫(避免留下垃圾產品)。上傳者與管理者權限相同。
- **「AI 寫出的時候就擋住」的做法(P4)**:
  1. LLM 的擷取輸出用 **json_schema 限制**:`product` 欄位是 `enum`(辨認庫現有正式名稱)加 `"__NEW__"`;選 `__NEW__` 時另附 `new_product_text`,該字串必須是使用者原文的子字串(伺服器核對)。LLM **無法輸出庫外的產品名稱**。
  2. 摘要卡與確認句裡的產品名稱、工單號、數量**由伺服器填入**,不取自 LLM 的自由文字。
  3. LLM 的口語回覆送出前先掃描:任何形如 `TN…數字…` 的產品片段或工單號,若不等於本輪伺服器已知的值 → 丟棄該回覆,改用伺服器模板。
- 管理者另可檢視辨認庫清單、停用產品(`retired` 的產品不再出現在候選,歷史資料不動)——屬選配,視 P3 時程決定。

### 3.6 計畫測試數量與數量對齊

- AI / 表單向使用者詢問「這批的計畫測試數量」:**必填**,1–99,999 的正整數。純數字用規則抽取;中文數字或縮寫(「一千二」「1.2k」)才請 LLM 轉換,**轉換結果一律請使用者確認**(「是 1,200 台嗎?」),LLM 不能直接決定數字。
- **「實測數量」一律用不重複 SN 數**,與 dashboard 的 `LATEST_SN_CTE`(每個 SN 只算最新一筆)一致。不用檔案數:77 個工單中 **38 個有重測,共 299 個重測檔**,用檔案數會多算。
- 對齊顯示:

| 項目 | 內容 |
|---|---|
| 計畫測試數量 N | 使用者輸入 |
| 本批不重複 SN M | 本批有效 log 的不重複 SN 數 |
| 上傳後該工單累計不重複 SN K | 該工單目前 DB 內的不重複 SN ∪ 本批 SN |
| 差異 K − N | 負數 = 尚缺、0 = 達成、正數 = 超出 |

- 範例(用你提供的檔案,DB 已有該 252 台):計畫輸入 252 → 本批 252、累計 252、**達成**;輸入 300 → **尚缺 48**;輸入 200 → **超出 52**。
- **為什麼要看「累計」**:有 3 個工單是分多天入庫,同一張工單可能分批上傳,只看本批會誤判成「尚缺」。
- **只顯示、不判對錯**(沿用姊妹專案做法):尚缺是正常的(分批、未做完);超出以醒目色標示。**已確認:超出也只用醒目色顯示,不升為警告、不需勾選確認。**
- **計畫數存放**:新資料表 `wo_plan(work_order PK, planned_qty, product_model, updated_by, updated_at, upload_id)`;`upload_log` 記錄每批輸入的計畫數與當時的前一個計畫數(`prev_plan`)。該工單已有不同計畫數 → ℹ「將更新 A → B」,成功後覆寫;**撤銷該批時還原前一次的計畫數**。既有 77 張工單沒有計畫數(NULL),不做回填。
- `NOWO` 批次也要問(每批獨立的偽工單,計畫數 = 這批預計上傳的台數)。
- 目前 dashboard 沒有任何地方使用計畫數;本次只負責收集與對齊顯示,之後若要在工單頁顯示達成率是另一項小功能。

## 4. 驗證規則(伺服器端,表單與對話共用;commit 時重跑,不信任前端)

| 代碼 | 規則 | 等級 | 備註 |
|---|---|---|---|
| R1 | 沒有任何有效檔名的 log | ❌ | 檔名須符合 `log_parser.parse_filename` |
| R2 | 產品類別為空,或不符 §3.3 的輸入形狀 | ❌ | 桌面版必填但無格式檢查。形狀符合後再經辨認庫轉成正式名稱(§3.4) |

| R4 | 產品形狀正確、TN 編號從未使用過,但**不在辨認庫**(新產品) | ⚠ | **上傳者、管理者皆可新增,不需核准**(已確認)。確認後以 §3.4 的正式名稱寫入辨認庫。保留「我確認這是新產品」勾選當防手誤 |

| R6 | 工單日期晚於今天 | ⚠ | 工單日期早於 log 日期是常態(實測差距 −6 ~ +469 天),所以不拿來跟 log 時間比對 |

### 10.2 目前沒有阻擋項

先前列的待確認事項已全部定案(見 10.1)。僅留兩點**我的解讀**,若不符請告訴我,改動都很小:

1. **「4. 不用」**:你回覆的是「TLS 憑證來源與 nginx 連接埠」這一題,我把它解讀為**連 nginx 也不加**(取代你先前「照建議」的 nginx)。理由:沒有 TLS,nginx 就只剩上傳大小與串流兩個用途,而這兩者在應用程式內即可處理,還能省下一個容器和一個連接埠。若你仍想保留 nginx,告訴我即可。
