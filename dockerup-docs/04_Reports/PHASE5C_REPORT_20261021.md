## 2. 今日頁

**範圍**：今天 = 測試站時鐘的日曆日（單班，Q3）；上班時間取自設定頁（預設 07:00–19:00）。不跟篩選列，是整條線的狀態。右上角的 ◀ ▶ 可看其他測試日（`#today?day=2026-01-13`），給電腦前的人用。

**狀態橫幅**：燈號取最嚴重的原因，依序為：
1. 今天有測的工單是紅燈或黃燈：顯示該工單已存的一句話狀態；
2. 今天的 FAIL 還有待處理的；
3. 上班時間內超過 N 分鐘沒有新測試（設定頁新增「今日頁：多久沒有新測試轉黃燈」，預設 30 分鐘；要當天已經開始測才判斷）；
4. 近 1 小時產出低於每小時目標的 80%（與工單狀態用同一個「落後目標 %」設定）。

橫幅下方是今天每張工單的小卡片（今日台數、良率、累計 / 計畫），點了進工單詳情。今天還沒有測試時，橫幅寫「今天尚無測試・最後測試 10/01 16:59」。

**6 個數字**

| 數字 | 內容 |
|---|---|
| 今日已測 | 今天的台數；只有一張工單且有計畫數時，顯示「工單累計 / 計畫，還差 N」 |
| 良率 | 今天的良率，▲▼ 與前一個測試日比較 |
| FAIL 待處理 | 今天的失敗機台中，處置還是「待處理 / 待重測」的台數；另列已處置台數、前 7 天還沒處理的台數 |
| 近 1 小時產出 | 最近 60 分鐘的台數 / 該時段主要工單的每小時目標 |
| 最後測試 | 幾分鐘前；超過設定的分鐘數轉黃燈 |
| 2.4G / 5G 平均 | 今天的平均吞吐量 |

**4 張圖**：良率趨勢（最近 14 個測試日；少於 10 台的日子不畫良率點，免得 1 台 FAIL 畫成 0%）、每小時產出 vs 目標（目標線跟著每小時的主要工單）、FAIL 原因 Top（當天與近 7 天）、每月台數。

**角色落地**：網址沒有指定頁面時，沒登入（含大電視）→ 今日；管理者 → 趨勢；上傳者 → 上傳 Log；RD → 進階分析（5F-2）。

## 3. FAIL 處置

**處置狀態**

| 狀態 | 誰設定 | 算待處理 |
|---|---|---|
| 待處理 | 預設 | 是 |
| 待重測 | 手動 | 是 |
| 已送修 / 交 RD | 手動 | 否 |
| 已結案（需備註，例如報廢） | 手動 | 否 |
| 重測通過 | **自動**：這台之後的測試通過 | 否 |
| 已重測 | **自動**：這台之後又測過；處置登記在最後一次 FAIL | — |

- 任何登入的帳號（上傳者、RD、管理者）都能改（§9.2 的假設：不另開班長角色）；沒登入只能看。
- 每次變更記在異動紀錄（誰、何時、前 → 後、備註），FAIL 詳情視窗看得到。改回「待處理」就不留資料列。

**建議動作**（規則，不呼叫 LLM）

| 情況 | 建議 |
|---|---|
| 之後重測已通過 | 不需處理 |
| 之後又測過 | 看最後一次測試 |
| 同一工單、同一現象，前後 60 分鐘內台數 ≥ 設定頁的「連續 FAIL 台數」（預設 3） | 先查測試站（N 台） |
| 第一次失敗（7 類可重測的現象） | 重測一次 |
| 連續失敗 2 次以上，或規則認不出來 | 交 RD / 送修 |
| RD 在進階分析寫了指示（5F-2） | 顯示 RD 的指示 |

滑鼠停在建議上會看到分類表的詳細建議（例如「重測仍 FAIL 交 RD 檢查天線 / 射頻匹配」）。

## 5. 順手修正

- **失敗清單的「測試序列」底線沒顯示**（5F-1）：列表少回傳「這一次是第幾筆」，底線一直不會出現。已補，連帶讓「連續失敗 2 次」的判斷正確。
- **LLM 主機換了模型**：10.20.30.23 現在跑的是 Qwen3.8-27B（不是設定檔寫的 Qwen3.6-35B-A3B）。實測一般回覆 2–3 秒、吞吐 36 tokens/s，速度沒問題；但這台 LLM 也有別的系統在用，忙的時候追問會等到 60 秒逾時（畫面顯示「AI 回答失敗，請稍後再試」）。已改為記錄伺服器實際回報的模型名稱；瀏覽器測試遇到 LLM 忙碌會重試一次。
- 先前兩支瀏覽器測試的檢查方式更新：AI 標籤數量改為和 API 比對（筆記在 30 分鐘節流期間會暫時顯示規則句，這是降低 LLM 用量的設計）；今日頁也用了同樣的圖表區塊，選擇器改為限定在趨勢頁。
