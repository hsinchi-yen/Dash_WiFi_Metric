## 3. 做了什麼

**分類規則**(`services/fail_rules.py`,純函式)
- 依 log 結構逐段解析:每個頻段的門檻、目標 SSID、每次嘗試的 Mbps / RSSI、無資料、連線錯誤、頻段總結;BT 結果、找不到裝置、`Host is down` 等錯誤;站別(Port、SSID Group)。
- **噪音行一律不當原因**:`wlan0 interface not found. Loading driver`(223 筆 FAIL 中 220 筆都有,PASS 也有)、`No IGD UPnP`、`Can't deallocate console`、核心驅動訊息等。
- 兩個從資料裡看出的特例:
  - WiFi 失敗後腳本直接結束、**BT 根本沒測**(總結寫 BT FAIL):不另算 BT 失敗,只標「BT 未測」。
  - **測試中途板子重開機**(log 出現開機畫面):歸「log 不完整 / 測試中斷」,證據行就是重開機那一行。
- 與桌面版解析器存的頻段結果交叉比對:每個被標失敗的頻段都有對應的分類,0 筆不一致。

**分類記錄**(新表 `fail_analysis`,每次 FAIL 一筆;分類表 `fail_taxonomy`,8 類,含中英名稱、說明、建議動作、可能環節)
- 重測結果:`重測後通過` / `重測仍失敗` / `未重測`,以及同一 SN 的測試序列(例如 `FFP`)。
- 環節(板子 / 天線 / 夾具 / AP 環境 / 韌體 / 測試站 / 未知)**留給 RD 確認**,規則不填(Q32)。
- 自動維護:每分鐘掃描一次新的 FAIL(桌面版寫入的也會被抓到)、網頁上傳完成後立即掃描;測試資料被舊 DB Tweak 刪掉,分類記錄也會跟著清掉。

**LLM 只處理規則沒命中的**(Q36)
- 只給 LLM 過濾掉噪音的結果 / 錯誤行,它只能從分類表選一類,並引用 1–3 行原文;伺服器檢查每一行**確實存在於 log、內容相符、不是噪音**,不符就維持「未分類」。
- 測試結果:一份只有「wlan firmware refused to start radio」的假 log,LLM 歸為「連不上 AP」並引用了正確的那一行(信心 0.95)。分類表目前沒有「韌體 / 射頻啟動失敗」這類,所以它選了最接近的;**LLM 的分類都標記來源,留給 RD 確認或改類**(5F-2 可新增類別)。

**RD 角色**
- 帳號管理新增角色選擇:上傳者 / RD。RD 可讀所有資料(含所有上傳批次),**不能上傳 log、不能新增產品**,不是管理者。
- 變更角色會讓該帳號登出,下次登入即為新角色;變更記在異動紀錄。

**畫面**
- **失敗清單**:「原因」改為「失敗現象」(滑鼠停留可看證據行與建議動作),新增「測試序列」(F / P,底線是這一次)與「站別」。
- **工單詳情**:新增「失敗分類」卡(每類的次數、台數、重測結果)與站別分布;FAIL 數字格寫出仍失敗機台的現象;失敗機台清單同樣顯示現象、序列、站別。
- **結案報告**的事實改用分類(每類次數、重測後通過、仍失敗)與失敗集中的站別;77 張報告已在背景依新事實重寫。

## 5. 順手修正:日期篩選只算第一天

`/api/overview`、工單、失敗清單、RF、產出分析的日期參數 `date_from` 與 `date_to` 共用同一個參數物件,FastAPI 因此只認得一個參數,兩邊都收到起始日。結果是**本週、本月、自訂範圍都只顯示第一天**(例如 9 月只算到 9/1 的 540 台,實際 4,734 台)。這是階段 3 起就存在的錯誤,只在本機、沒有部署過。已改為每個參數各自一個,並加測試防止再發生。golden 40/40 不受影響(它比的是舊 API)。
