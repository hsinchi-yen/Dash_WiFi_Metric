# Final Improvement Plan — WiFi YFP Dashboard 最終優化方案

日期:2026-10-21 ・ 審閱對象:本機 `wifi-local` 上的階段 1–4 成果(http://10.88.90.136:8000,資料與正式機逐列相同)
審閱方式:以三種角色各走一遍每個頁面(1920×1080 大電視、390 寬手機、Dark/Light、EN/中文),並讀過 API、上傳流程、AI 報告的實際輸出。

## 0. 一頁摘要

**做得好的(保留)**
- 骨架對齊 Solo PIXI:字大、首頁不捲動、Dark/Light、EN/中文、閒置輪播、資料更新時間 + Refresh。
- 上傳流程把桌面版的 Database Upload 完整搬進來,R1–R16 規則三層防呆(畫面、API、資料庫筆數)經 149 + 13 項邊界測試。
- 產品辨認庫、帳號與稽核、AI 助理「規則決定、LLM 只說話」的分工正確,擋得住 LLM 自作主張。
- 舊 API 數字經 golden 40/40 驗證不變;AI 報告預先產生,開啟秒出。

**主要落差(照角色)**

| 角色 | 他要在 5 秒內回答的問題 | 現在的落差 |
|---|---|---|
| **產線班長** | 今天/這一班測了多少、還差多少、有沒有 FAIL 要處理、哪一站/哪一小時掉速 | 首頁是「一張工單的統計」,不是「今天的狀況」;沒有燈號、沒有目標線、沒有「下一步動作」;FAIL 只有清單沒有處置建議;Management 群組與 RF 指標對他是噪音 |
| **管理者** | 哪些工單異常、和上一批/同產品比如何、本週/本月趨勢、誰上傳了什麼 | 看板只能「一次看一個範圍」,沒有比較;工單表 13 欄無狀態/達成率;AI 報告五段制式文字,**會編造門檻與日期**(見 §2.6);上傳紀錄與看板互不連結 |
| **上傳者** | 這批 log 要怎麼傳、傳完有沒有問題 | 一頁三步驟太長要捲動;「計畫測試數量」不一定是上傳者知道的事;AI/表單並列不知道用哪個;傳完沒有「去看這張工單」的出口 |
| **RD 研發** | 這批 FAIL 是什麼現象、是板子/天線/夾具/測試站哪一個、同一現象在哪些產品/站別/時段出現、重測後有沒有好 | 失敗只有一個粗略的「原因」欄(2.4G 低 / 5G 低 / BT / 無資料),**沒有分類記錄、沒有錯誤碼、沒有證據行、沒有站別、沒有重測結果**;沒有可以依現象查詢的視窗(§2.9) |

**建議的三條主軸 + 一個獨立面向**(細節在 §3–§5,方向由 §6 的問題定案)
1. **以「人」而不是「資料表」組織頁面**:班長的「今日/班次」首頁 + 管理者的「趨勢/比較」頁 + 點進去的「工單詳情」頁(把現在散在 5 頁、靠篩選串起來的資訊收在一頁)。
2. **把管理分頁變成任務流**:上傳三步驟改精靈式(一步一畫面)、計畫數由管理者預設、上傳完成直接跳工單詳情;Management 群組登入後才出現。
3. **edge LLM 從「寫報告」改成「判讀 + 提醒 + 問答」**:每張進行中工單一句話狀態、FAIL log 原因歸類與處置建議、交班摘要、自然語言查詢;全部「規則先算、LLM 只口語化、數字只准來自事實表」,預先產生,離線退回規則文字。
4. **RD 問題分流(§2.9)**:固定畫面給班長與管理者;**失敗現象的分類記錄**(錯誤碼、證據行、站別、重測結果)與一個 **「進階分析」視窗**給 RD 查詢、歸類與追蹤。已用正式資料的 223 筆 FAIL 驗證:規則可以自動分出 9 類,覆蓋 98%。

## 2. 逐頁審閱

### 2.1 儀表板(Dashboard)
**現況**:7 個大數字(良率、台數、PASS、FAIL、重測率、2.4G/5G 平均)+ 4 張圖(良率趨勢、PASS/FAIL、每月台數、吞吐量分佈);預設最新工單;篩選列(All/Today/This Week/This Month/Custom + 產品 + 工單)。

**觀察**
1. 最大的字是「良率 100.00%」,底下一行「No planned quantity」:**77 張工單只有上傳者輸入過計畫數的才有值**,大多數時候這行是噪音,卻佔了最醒目位置。
2. 100% 綠色沒有「相對於什麼」:上一張同產品工單是多少?本月平均是多少?班長與管理者都需要一個參考點。
3. 標題旁小字「Work order 5101-260820009」是目前唯一告訴你範圍的地方;大電視 3 公尺外看不到。
4. 四張圖對班長的價值:良率趨勢 ✔、PASS/FAIL 圓餅 ✘(同一數字第三次出現)、每月台數 ✘(管理者月報用)、吞吐量分佈 △(RF 頁已有)。班長真正要的「今天每小時產出 vs 目標」「FAIL 原因 Top 3」不在首頁。
5. 「重測率 0.20%・1 units retested」永遠接近 0(桌面版 log 幾乎沒有重測),是一個長期為零的大數字。
6. 沒有「狀態燈」:這張工單現在是正常 / 注意 / 異常,需要門檻(良率 98/95 已有,但沒有吞吐量、重測、FAIL 連續等門檻)。
7. 手機版 7 數字 + 4 圖排成一長條,可看但不好用。

**建議**
- 首排改為「狀態橫幅」:燈號 + 一句話(規則產生,LLM 口語化,§4 L1)+ 範圍(工單/產品/期間)大字顯示。
- 7 數字改為「班長 5 數字」:已測 / 計畫(或目標)、良率(附上一批 ▲▼)、FAIL 待處理、本小時產出(vs 目標)、最後一筆測試距今;管理者視圖保留吞吐量平均。
- 圖:良率趨勢(保留)、今日每小時產出 vs 目標節拍(新)、FAIL 原因 Top(新)、吞吐量分佈(保留或移到 RF)。
- 「計畫數」未設定時改為小字「未設定計畫(管理者可在工單頁設定)」;或完全隱藏。
- 重測率移到工單詳情頁;首頁不放長期為零的數字。

### 2.2 工單(Work Orders)
**現況**:單一表格 13 欄(工單、產品、最後測試、台數、PASS、FAIL、良率、重測率、2.4G、5G、歷時、台/小時、AI 報告按鈕)。
**觀察**:欄位對班長太多(他要 5 欄);沒有「狀態」(進行中 = 最近 2 小時內有測試 / 已完成 / 停滯 N 天);沒有「達成」(已測/計畫);AI 報告每張要點開才知道結論;無法依產品分組或比較兩張工單;無法從工單直接到該工單的 FAIL / RF / 上傳紀錄。
**建議**:
- 加欄:狀態標籤、達成率(有計畫數時)、AI 一句話結論(預先產生,滑鼠停留看全文)。
- 欄位分「基本」(班長預設)與「進階」(管理者切換,記住選擇)。
- 點工單列 → **工單詳情頁**(新):事實卡、狀態判讀、良率/產出趨勢、FAIL 清單、RF 摘要、上傳批次、AI 報告與追問、「與上一張同產品工單比較」。這一頁取代現在「用篩選把五頁串起來」的操作。
- 勾選兩張 → 比較(數字差異、趨勢重疊)。

### 2.3 失敗清單(Fail List)
**現況**:表 11 欄(時間、工單、產品、SN、MAC、原因、2.4G、5G、RSSI Δ、次數、下載 log),搜尋,分頁。
**觀察**:原因是規則推論(frontend/stats `FAIL_REASON_SQL`),類別粗(2.4G 低 / 5G 低 / BT / 無資料);沒有分佈;不知道這台後來有沒有重測 PASS(資料裡 299 個重測檔);班長拿到 FAIL 的第一個問題是「要重測、換站、還是報修?」沒有答案;同一站/同一小時連續 FAIL 看不出來。
**建議**:
- 頂部 tiles:FAIL 原因分佈、重測後 PASS / 仍 FAIL、今日新增 FAIL。
- 欄:加「處置狀態」(待處理 / 已重測 PASS / 已報修,可由班長勾選)與「建議動作」(規則 + LLM,§4 L2)。
- 點 FAIL → 側欄顯示 log 關鍵段(錯誤行、RSSI、頻道)而不是只有下載。
- 「同站連續 FAIL ≥ 3」規則 → 狀態橫幅提醒。

### 2.4 RF 分析
**現況**:三個分頁(2.4G / 5G / BT),7 tiles(平均、中位數、P5、標準差、RSSI、頻段 FAIL、無資料)+ 時間趨勢 + 分佈 + 5G 不穩定 Top 20。
**觀察**:這是工程師頁,內容正確;但沒有門檻(P5 低於多少算差?標準差多少算不穩?),沒有「與同產品歷史比較」,班長看不懂。「RSSI before → after」顯示「—」(資料無 RSSI before)。
**建議**:每個 tile 加門檻帶色與一行解讀;加「同產品歷史中位數」參考線;「這代表什麼」一句判讀(§4 L12);RSSI 無資料時隱藏 tile 而不是顯示「—」。

### 2.5 產出分析(Production)
**現況**:5 tiles(最快/最慢工單、平均每台時間、平均產出、工單數)、產出率柱狀、每台時間分佈、每小時產出、工單指標表。
**觀察**:沒有班次(早/中/晚)概念;每小時產出沒有目標線(節拍);只有一張工單時最快 = 最慢;「≤ 30 days each」註解看不懂。
**建議**:班次設定(管理者設起訖時間)→「本班次產出 vs 目標」;每小時圖加目標線與「落後/超前」判讀;單工單時 tiles 改為「本工單 vs 同產品平均」。

### 2.6 AI 報告
**現況**:每張工單預先產生中英兩份五段式 markdown(概況、良率等級、性能、失敗原因、結論);可複製、下載、重新產生。
**實際輸出中發現的問題**(讀了 4 份已存報告):
- **門檻編造**:報告寫「依內部品質門檻(≥99.2% 正常,98.5–99.19% 警告,<98.5% 告警)」——這組門檻來自舊的 `ai_summary_helper.py`,**與看板的 98 / 95 不一致**;同一個系統兩套標準。
- **日期與署名編造**:「報告日期:2023-10-27」「測試工程師:[您的姓名/AI助手]」「Date: 2024-06-04 (inferred from work order ID)」——模型從工單號猜日期,猜錯年份。
- **無異常也寫滿五段**:100% 良率的工單仍寫「無需根因分析」「建議直接進入下一階段生產或包裝出貨」——制式廢話,管理者讀三份就不想讀了。
- 沒有與上一張工單或同產品歷史的比較;不能追問;中英文各跑一次 LLM(各 10–30 秒),內容卻可能不一致。
**建議**(= 原計畫階段 5,重新定義):事實表由伺服器產生並**直接顯示**(不靠 LLM 重述);LLM 只寫「異常與建議」段,json_schema 限制輸出欄位,**數字必須來自事實表(伺服器核對,出現事實表沒有的數字就丟棄)**;無異常 → 三句話;自動附「與上一張同產品工單比較」;可追問(問題限於本工單事實);門檻統一用看板的 98/95(或由你重新定義,§6 Q8)。

### 2.7 上傳 Log
**現況**:登入 → ① 選 zip/資料夾(事實卡、推斷提示、忽略清單)→ ② AI 對話或表單確認產品/工單/計畫數(規則訊息、對齊卡、確認勾選)→ ③ 進度、結果、CSV、撤銷 → 紀錄表。
**觀察**
- 三步驟在同一頁,1080p 要捲動兩屏;頂部說明文字四行,老手每次都看到。
- 「計畫測試數量」是**管理者/生管知道的數字**,上傳者(測試站人員)常常不知道;現在卻是上傳者必填。
- AI 對話與表單並列 + 「改用表單」按鈕:新手不知道該用哪個;AI 一回合 4–6 秒,填三個值要 15–20 秒,比表單慢。AI 的價值其實在「幫你對照、解釋、抓錯」,不在「幫你打字」。
- 對齊卡要等三個值都填完才出現;R8「檔名推斷不同」警告很有用但藏在清單中。
- 上傳完成後沒有「查看這張工單」「看 AI 判讀」的出口;紀錄表 11 欄過寬;新產品標籤好。
- 選資料夾用 `webkitdirectory`,Firefox 不能拖放資料夾(已知)。
**建議**
- 改精靈式:一步一畫面(選檔 → 確認 → 結果),上一步摘要收成一列;說明文字收進「?」。
- 計畫數改為「管理者預先在工單設定(或從 ERP 匯入)」,上傳者只看到「這張工單計畫 300,本批 252,累計 252」並確認;沒有預設時才要求輸入(§6 Q16)。
- 預設表單 + 右側「AI 助理」面板:AI 主動做三件事——對照檔名推斷與輸入、解釋每條 ⚠、上傳後給「這批 vs 該產品歷史」判讀;對話輸入保留給想用的人。
- 完成畫面:結果四格 + 「查看工單 5101-…」「AI 判讀」按鈕;紀錄表精簡為 7 欄,其餘進詳情。

### 2.8 產品名稱、資料庫維護、帳號管理
- 產品名稱:良好。上傳者視圖隱藏「來源 / 備註 / 操作」欄;加「最近 30 天台數」欄讓管理者看出哪些產品還在產。
- 資料庫維護:加「依上傳批次刪除」(現在要去上傳紀錄撤銷)、「匯出目前篩選為 CSV」;刪除前顯示影響的工單統計;每列兩顆按鈕改為單一「⋯」選單減少誤點。
- 帳號管理:加「最近一次上傳失敗 / 撤銷」提醒;「看紀錄」已可用。
- 全域:Management 群組**登入後才顯示**(班長看板不出現);側欄底部登入框;首次進入依角色落地(班長 → 今日頁、管理者 → 趨勢頁、上傳者 → 上傳頁)。

### 2.9 RD 問題分流:失敗現象的分類記錄與「進階分析」視窗

**需求**:固定顯示的畫面給班長與管理者;RD 需要的是「這批 FAIL 是什麼現象、是哪個環節、在哪些產品/站別/時段重複出現、重測後有沒有好」——要有**分類記錄**(錯誤碼、現象、證據),並有一個可以依現象查詢的視窗。

**有辦法整理嗎?有。** 先用正式資料(64,181 筆,其中 223 筆 FAIL、299 次重測)實際驗證 log 裡有哪些可分類的訊號:

| log 裡實際存在的訊號 | 出現在 FAIL 的筆數 | 也出現在 PASS 的比例 | 判定 |
|---|---|---|---|
| `Result: FAILED (7 MBits/sec < 10 MBits/sec) - RSSI after test: -27 dBm`(有量到、低於門檻,含實測值 / 門檻 / RSSI) | 201 | 35%(PASS 的前幾次 attempt 也會出現) | **主要分類依據**:以該頻段最後結果 + `band_result_24g/5g` 為準 |
| `Result: FAILED (No valid throughput data after multiple attempts)`(連上了、iperf 沒資料) | 36 | 5% | 分類依據 |
| `ERROR: Failed to connect to 2.4G/5G band WiFi`(連線/關聯失敗) | 6 | 0% | 分類依據 |
| `Bluetooth Test Result: FAILED (All 6 attempts failed)` + `Can't connect: Host is down` | 9 | 0% | 分類依據 |
| `ERROR: BT device (hci0/hciX) not found!` / `Bluetooth initialization failed after 20 seconds` | 7 | 0% | 分類依據 |
| `Fatal server error` / `_XSERVTrans…` / `Cannot get device settings` | 7 | **21%** | 噪音(測試站腳本訊息),不能當原因 |
| `wlan0 interface not found. Loading driver` / `can't open /tmp/serverip` / `No lease, failing` / `Network is unreachable` / `Can't deallocate console` | 26–221 | **19–100%** | 噪音,PASS 也有;只能當「站別環境」線索 |
| 標頭:`Port: /dev/ttyUSB2`、`SSID Group: grpb (STA group B)`、`Target SSID: PD-RF-QC-5-STA-B`、`Band Priority`、`Iperf duration`、門檻值 | 每筆都有 | — | **站別 / AP / 測試設定**可以從這裡擷取,目前沒有存進資料庫 |
| 重測序列(同 SN 多次):`FP` 160、`PP` 76、`FFP` 9、`FF` 4、`FFFP` 3、`FFFFFP` 1 … | — | — | 「重測後 PASS」= 暫時性 / 邊緣;「連續 FAIL」= 持續性不良。這是 RD 最需要、現在完全沒有的欄位 |

用上面的訊號寫規則,223 筆 FAIL 的分佈(草案分類法,RD 可以改名、合併、新增):

| 代碼 | 現象 | 筆數 | 分類依據 | 典型下一步(給班長的建議動作) |
|---|---|---|---|---|
| `WIFI_TP_LOW_24G` | 2.4G 吞吐量低於門檻(有連線、有量到) | 150 | `band_result_24g=false` + 最後 `Result: FAILED (x < y)` | 重測一次;重測仍 FAIL → RD(天線 / 射頻匹配) |
| `WIFI_TP_LOW_5G` | 5G 吞吐量低於門檻 | 14 | 同上,5G | 同上 |
| `WIFI_NO_TP_DATA` | 連線成功但 iperf 無有效資料 | 35(其中 30 同時有 TP_LOW) | `No valid throughput data` | 檢查測試站 iperf 伺服器 / AP;同站連續出現 → 站別問題 |
| `WIFI_ASSOC_FAIL` | 連不上 AP(關聯 / DHCP 失敗) | 6 | `Failed to connect to …G band` | 檢查 AP 與 SSID 設定;單台 → 板子 |
| `BT_PING_FAIL` | BT 有裝置但 l2ping 全部失敗 | 9 | `Bluetooth Test Result: FAILED (All … attempts)` | 檢查對端 BT 參考裝置;單台 → 板子 BT 天線 |
| `BT_DEV_NOT_FOUND` | 找不到 BT 裝置(hci0) | 7 | `BT device … not found` / `initialization failed` | 板子 BT 模組 / 韌體 → RD |
| `LOG_INCOMPLETE` | log 空白 / 截斷 / 沒有任何結果段 | 4 | 長度 < 5 KB 或無 `Final Result` | 測試站當機或拔線;重測 |
| `MULTI` | 同一筆同時命中兩類以上(例如 2.4G 低 + BT 失敗) | 約 5 | — | 依最嚴重者 |
| `UNKNOWN` | 規則沒命中 | ≈2 | — | 交 LLM 歸類(白名單 + 證據行)→ RD 確認 |

另外兩個**正交的屬性**,每筆都記:
- **重測結果**:`PASS_ON_RETEST`(FP、FFP…)/ `PERSISTENT`(FF、FFF…)/ `NOT_RETESTED`。
- **站別**:`Port`、`SSID Group`、`Target SSID`(= 哪台 AP / 哪個測試站);同站同時段連續 FAIL 是站別問題而不是板子問題,現在看不出來。

**資料模型**(只新增,`test_record` 不改)

| 表 | 內容 |
|---|---|
| `fail_taxonomy` | 代碼、中英名稱、現象描述、嚴重度、建議動作、是否啟用、由 RD 維護(可新增代碼、合併、停用) |
| `fail_analysis`(每筆 FAIL 一列,FAIL 之外的「警告」也可記) | `record_id`、`category`、`secondary_categories`、`band`、量測值(實測 Mbps、門檻、RSSI、attempts)、`station_port`、`ssid_group`、`target_ssid`、`retest_outcome`、`evidence`(引用的 log 行與行號,JSON)、`classifier`(rule / llm / rd)、`confidence`、`rd_status`(new / confirmed / reclassified / closed)、`rd_owner`、`rd_note`、`updated_at` |
| `fail_signature`(選配) | 正規化後的錯誤行簽章 → 類別的對照表,RD 新增一條簽章就等於教會規則 |

**流程**:新資料進入(網頁上傳 commit 後,或排程掃描桌面版寫入的新 FAIL)→ 規則擷取訊號與站別 → 命中就分類;沒命中 → LLM 以白名單 enum 歸類並**必須引用 log 原文行**(伺服器核對該行確實存在)→ `classifier=llm`、附信心度 → RD 在進階分析視窗確認 / 改類 / 加註;RD 的改類回寫 `fail_signature`,之後同簽章自動分類。既有 223 筆 FAIL 與 299 次重測第一次全部回填。

**「進階分析」視窗(RD 專用,固定畫面不受影響)**
- 入口:Management 群組底下「進階分析」,或工單詳情的「RD 分析」分頁;權限:新角色 `rd`(可讀全部資料、可改分類與註記、不能刪資料、不能上傳)與管理者。
- 篩選:產品、工單、期間、分類、頻段、站別(port / SSID group / AP)、重測結果、RSSI 區間、吞吐量區間、分類來源、RD 狀態。
- 視圖:① 柏拉圖(分類 × 產品 / 站別 / 週);② 交叉表(分類 × 站別、分類 × 產品、分類 × 時段);③ 清單(每筆:SN、現象、證據摘要、量測值、重測結果、RD 狀態);④ **SN 歷程**(同一 SN 的每次測試時間線,含 MAC、站別);⑤ **log 檢視器**(整份 raw_log,證據行高亮,可左右對照兩筆 log);⑥ 「相似案例」(同簽章 / 同站同時段)。
- 動作:改分類、加註、指派、結案;匯出 CSV / 匯出該篩選的 log 打包;「問 AI」(限本篩選範圍的事實:這群 FAIL 的共同點、可能原因、建議的下一個檢查)。
- LLM 的角色(§4 L2 的延伸):歸類未知案例(白名單)、摘要一群 FAIL 的共同點、把 RD 的結論寫成給班長看的一句建議動作;**不做**:自創類別、改數字、決定結案。

**對固定畫面的回饋**:班長的 FAIL 清單顯示「現象 + 建議動作」(來自分類);管理者的工單詳情顯示「失敗分類分佈」;RD 結案的結論(例如「10/01 12:00–14:00 站 B AP 干擾」)以一句話回寫到該工單的狀態判讀。

## 4. edge LLM 可加入的協助與判讀

前提:LLM 是 llama.cpp 上的 Qwen3.6-35B(thinking 關閉),一次回覆 4–6 秒、報告 10–30 秒,單一佇列;沒有 GPU 擴充。所以原則是:**規則算數字、LLM 只口語化;能預先產生就預先產生;輸出用 json_schema 限制;每句話附依據;離線退回規則文字**。這些原則在上傳助理已驗證有效(LLM 無法輸出辨認庫外的產品)。

| # | 協助 | 做法 | 觸發 / 延遲 | 價值對象 | 可行性 |
|---|---|---|---|---|---|
| **L1** | **工單狀態一句話** | 規則算 flags(良率 vs 門檻、FAIL 連續、吞吐量低於歷史 P50、停滯、落後目標)→ LLM 以 1 句中/英說明 + 燈號 | 每張進行中工單每 5 分鐘預產(mv_unit 刷新後);≈5 s/張,背景 | 班長、管理者 | 高(沿用 ai_reports 佇列) |
| **L2** | **FAIL 分類與處置建議**(§2.9) | 規則先分類(9 類,覆蓋 98%)並擷取量測值 / 站別 / 重測結果;規則沒命中的才給 LLM,從 `fail_taxonomy` **白名單 enum** 選一個 + 必須引用 log 原文行(伺服器核對)+ 信心度;建議動作來自分類表,LLM 只口語化 | FAIL 寫入後背景;規則毫秒級,LLM ≈5 s/筆(每天 FAIL 少) | 班長、RD、工程師 | 高;已用 223 筆 FAIL 驗證規則 |
| **L2b** | **FAIL 群集摘要**(RD) | 進階分析的篩選結果(例如「站 B、10/01、2.4G 低」20 筆)→ 事實(量測分佈、站別、時段、重測結果)→ LLM 寫共同點與建議的下一個檢查 | RD 按「問 AI」時,≈8 s | RD | 高 |
| **L3** | **結構化結案報告**(階段 5) | 事實表伺服器產生;LLM 只填「異常、可能原因、建議」三欄(json_schema);數字伺服器核對;附上一張同產品比較;可追問 | 工單 24 小時無新資料後自動產生;≈15 s | 管理者 | 高(替換現有報告) |
| **L4** | **交班摘要** | 班次結束時彙整該班工單事實 → 5 行摘要(產出、良率、FAIL 處置、未完成、提醒) | 每班次一次,預產 | 班長 | 高(需班次設定) |
| **L5** | **週報 / 月報** | 期間事實(各產品/工單)+ 圖表快照 → LLM 寫摘要段;下載 .md / .pdf | 每週一 / 每月 1 日預產 | 管理者 | 中(PDF 需加套件) |
| **L6** | **問看板(Ask the dashboard)** | 自然語言 → LLM 轉成**受限查詢物件**(指標、期間、工單、產品;json_schema,不給 SQL)→ 伺服器查 mv_unit → 回答數字 + 顯示對應圖 | 互動,5–8 s | 管理者、班長 | 中;範圍要限定在既有指標 |
| **L7** | **上傳後即時判讀** | 上傳完成 → 這批 vs 該產品歷史(良率、吞吐量 P50、FAIL 率)→ 一段判讀 + 是否要通知管理者 | 上傳 done 後背景,≈5 s | 上傳者、管理者 | 高(事實已在 upload_log) |
| **L8** | **異常提醒** | 規則偵測(吞吐量下滑 20%、同站連續 FAIL ≥3、重測率升、工單日期異常、長時間無資料)→ LLM 寫提醒句 → 狀態橫幅 / 通知 | 每 5 分鐘規則掃描 | 班長、管理者 | 高(規則);通知管道待定 |
| **L9** | **指標解釋** | 每個指標「?」→ 一句話解釋 + 本產品正常範圍;預先產生並快取,不即時呼叫 | 一次性 | 班長、新人 | 高 |
| **L10** | **上傳助理升級** | 從 log 內容讀測試站設定(SSID/頻道/AP/韌體版)→ 與該產品歷史設定比對 → 不同就提醒(「這批 5G 用 ch36,上批 ch149」) | analyze 時規則擷取,LLM 只說明 | 上傳者、工程師 | 中(需確認 log 內有這些欄位) |
| **L11** | **RF 判讀** | P5 / 標準差 / RSSI 與門檻、歷史比較 → 判讀句(「5G P5 低於歷史 30%,集中在 10/01 12:00,疑似該時段 AP 干擾」) | RF 頁開啟時用預產事實 | 工程師 | 高 |
| **L12** | **語音問答(手機)** | 瀏覽器語音轉文字 → L6 | 互動 | 班長 | 低優先(選配) |

**不建議做的**:讓 LLM 直接寫 SQL、讓 LLM 決定可否上傳、讓 LLM 即時生成首頁數字(延遲與一致性)。

## 6. 對齊問題(請逐題選擇;沒意見就用「建議」)

回覆方式:`Q1:B, Q2:A, …`,也可以在選項後面加備註。

### A. 使用者與情境
**Q1. 大電視(產線)主要給誰看?**
A. 班長與作業員(今日狀況) B. 管理者(趨勢) C. 兩者輪播 — **建議 A**:大電視只放「今日/班次」頁,管理者用電腦看趨勢。

**Q3. 班次怎麼切?**
A. 單班 B. 兩班(例 08–20 / 20–08) C. 三班 D. 不固定 — **建議 B**;班次時間放「設定」頁。

**Q4. 誰負責輸入「計畫測試數量」?**
A. 上傳者(現況) B. 管理者在工單頁預設 C. 從 ERP 匯入 D. 不需要計畫數 — **建議 B**(有 ERP 就 C):上傳者只確認。

A. 有,可定期匯出 CSV B. 有 API C. 沒有 D. 之後再說 — **建議 A**:每天一次 CSV 就能擋「不存在的工單號」並帶入計畫數。

**Q6. 介面語言預設?**

**Q7. 首頁改為「今日/班次」視角?**
